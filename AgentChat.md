- Recap: We began by deriving physical DPI from the monitor/virtualization ratio and fed it through the window + Skia/Vulkan stack. Each pass fixed one symptom but exposed others—first the editor grew 150% (window scaled too), then resize/math was corrected yet frames stayed soft, later swapchain extents, MSAA surfaces, and forced 1.5 DPR experiments distorted layouts or blew up renderpasses while the texture blur never improved.
- Findings: Logging proves we can measure both host and physical DPI, and we can coerce swapchains/bitmaps to allocate at 1.5×, but Skia still rasterizes at virtual resolution unless its image provider + renderpass attachments are rebuilt coherently. The last round introduced black backgrounds/tearing because attachments and framebuffers disagreed on pixel size—hence the visual chaos despite correct mouse math.
- Why revert: The regression set left the branch unable to render a usable UI (missing layers, validation errors) while still failing to deliver crisp output, so I reset to the last working baseline to remove those compounding side effects before continuing.
- New strategy: treat the pipeline like a binary search. Step 1, instrument the baseline to report actual SkSurface backing resolution vs. requested logical size so we know the current DPI ground truth. Step 2, locally hard-wire Skia’s device pixel ratio (via the surface matrix/image provider) without touching window/swapchain code—if that does not sharpen the frame, we know the issue lives entirely inside Skia. Step 3, if Skia responds, re-enable physical swapchain extents and adjust Vulkan renderpass/framebuffer creation in one focused patch so attachments, command buffers, and present images agree on the same pixel counts. After each stage we validate before moving deeper. Only once a step measurably increases resolution without layout drift do we keep it and proceed.
