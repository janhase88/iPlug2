# Windows Vulkan Validation Re-Audit

## Updated Context
- Startup and shutdown still trigger validation errors centered on queue acquisition, image layout transitions, and descriptor pool teardown.
- OBS, ASUS GTIII, and other overlays hook the Vulkan runtime; their layers generate additional warnings (e.g., descriptor pool free without `FREE_DESCRIPTOR_SET_BIT`). We document them but focus on defects attributable to iPlug2.

## Validation Findings (2024-xx-xx)
1. **`vkGetDeviceQueue` VUID-vkGetDeviceQueue-queueFamilyIndex-00384**
   - Fired immediately after device creation.
   - Root cause: validation cascaded from the feature-chain misuse below; once device creation emitted an error, subsequent queue queries triggered the follow-up warning even though the queue request itself matched the sole queue family we created.
2. **`vkCreateDevice` VUID-VkDeviceCreateInfo-pNext-06532**
   - The layer rejected a `VkDeviceCreateInfo` chain that appended both `VkPhysicalDeviceSynchronization2Features` and `VkPhysicalDeviceVulkan13Features`.
   - Vulkan 1.3 promotes Synchronization2 into the core struct, so the two feature structs must not appear together.
3. **`vkCmdPipelineBarrier` & layout transition VUIDs**
   - Skia emits `VK_IMAGE_LAYOUT_READ_ONLY_OPTIMAL` transitions whenever Synchronization2 is reported available.
   - Our renderer still records legacy `vkCmdPipelineBarrier` commands, so enabling Synchronization2 (or reporting Vulkan 1.3 support) causes validation to flag the unsupported layout/stage mask pairings.
4. **`vkCreateImage` extent.depth = 4**
   - Observed during third-party overlay initialization (GTIII-OSD). The stack trace points into their module; no iPlug2 allocation uses a depth of four for 2D swapchain surfaces.
5. **`vkFlushMappedMemoryRanges` size alignment**
   - Generated by OBS' graphics-hook layer performing sub-atom flushes; not emitted when overlays are disabled.
6. **`vkFreeDescriptorSets` missing FREE flag**
   - Also traceable to GTIII-OSD descriptor pool teardown. Our code does not create descriptor pools at present.

## Research Notes
- Khronos Vulkan 1.3 specification (§39.6.2/§39.6.3) requires either core 1.3 support or the `VK_KHR_synchronization2` extension before `VK_IMAGE_LAYOUT_READ_ONLY_OPTIMAL` and `VK_PIPELINE_STAGE_NONE` become valid enumerants.
- `vkEnumerateInstanceVersion` allows applications to negotiate the loader's highest supported API level so promoted core features remain available even when the extension strings disappear.
- Skia's Ganesh Vulkan backend (docs/ganesh/vk.md) expects `VulkanBackendContext::fMaxAPIVersion` to match the runtime so it can decide whether to issue Synchronization2-style barriers.

## Remediation Plan Execution
- [x] Distinguish between "extension string present" and "feature supported" inside `WinVulkanDeviceCoordinator`.
- [x] Query `VkPhysicalDeviceSynchronization2Features` via `vkGetPhysicalDeviceFeatures2` before device creation and persist the resulting struct.
- [x] Clamp the extension enablement array so we only append `VK_KHR_synchronization2` when the driver actually exposes the name.
- [x] Export the physical device's `apiVersion` through `VulkanContext` and set Skia's `fMaxAPIVersion` accordingly.
- [x] Document third-party overlay warnings so the user can differentiate them from iPlug2 regressions.
- [x] Disable Synchronization2 advertisement until our command buffer migration to `vkCmdPipelineBarrier2` is complete.
